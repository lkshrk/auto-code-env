## Cross-session-useful facts learned (durable, not just this repo)

- This h-cloud LiteLLM gateway (https://api.ai.h-cloud.lan/v1) requires the
  `openai/` prefix for EVERY model including Claude ones (e.g.
  `openai/claude-sonnet-5`), because it's a single OpenAI-compatible Responses
  API endpoint for all providers. `anthropic/claude-sonnet-5` or a bare
  `claude-sonnet-5` makes LiteLLM's own client-side provider inference route
  to the wrong native API shape and 404s -- NOT a gateway problem, a client
  request-construction problem. Model aliases available (checked via
  /v1/models): claude-opus-4-8, claude-opus-5, claude-sonnet-5,
  claude-haiku-4-5-20251001, claude-fable-5-1, claude-sonnet-5-high,
  anthropic-auto, plus the openai/gpt-5.x family used earlier.
- OpenHands SDK's LocalConversation requires an Agent object (wrapping an
  LLM), NOT a raw LLM directly -- passing a raw LLM causes a cryptic
  "'LLM' object has no attribute 'pop'" deep inside ConversationState.create.
- Agent needs `tools=get_default_tools()` from the separate `openhands-tools`
  PyPI package (not bundled with openhands-sdk) explicitly passed in. Without
  it, the agent has ONLY finish/think tools and will SILENTLY narrate task
  completion via `finish` without ever touching the filesystem -- a dangerous
  silent-failure mode that looks like success (plausible completion message,
  no error) but does nothing. Always verify real side effects
  (file exists, content matches) after any LLM acceptance test, never trust
  the model's own "I did X" narration.
- `LITELLM_API` env var in THIS agent-canvas sandbox is the raw key
  (`sk-...`), needs "Bearer " prepended manually for Authorization headers.
  (Contrast: inside a Coder workspace, an earlier session note showed the
  literal env var value already including "Bearer " -- these are two
  DIFFERENT secret injections in two different environments, don't assume
  they share format.)
- `omni tools list --format json` (native Omni CLI) reports real installed
  versions/states for every provider type without any external per-tool
  version-flag knowledge -- 306ms for 38 tools in one real test. This is the
  mechanism task 5's fix relies on.
- Coder's `insights/user-activity` API requires start_time at exact midnight
  UTC (day-granularity reports only), and aggregates by template, not
  workspace -- not usable for any real-time per-workspace signal.
- This agent's Kubernetes access (agent-sandbox-deploy skill) is scoped to
  the `agent-sandbox` namespace only; no read access to any other namespace,
  including wherever the real LiteLLM/other infra pods run.
